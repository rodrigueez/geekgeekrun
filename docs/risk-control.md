# 风控边界与运行节奏

本文记录本项目对 BOSS 直聘风控的观测结果、错误处置方式和推荐设置。数据截至 2026-11-12，均来自本机实测或公开项目代码，不构成对平台规则的保证。

## 1. 风控分层

| 层 | 触发物 | 表现 | 恢复方式 |
|---|---|---|---|
| 环境层 | 指纹、UA、`navigator.webdriver`、CDP 暴露、headless | 页面跳 `about:blank`，或直接进入 `security.html` | 换真实浏览器环境；本项目依赖 `puppeteer-extra` + stealth |
| 签名层 | 缺 `zp_token` / `token` / `traceid` / 带 `_security_check` 的 referer | 第一个请求就 `code 37` | 必须由页面自己发请求，不能手工构造 |
| 频率层 | 短窗口内请求过多 | `code 37 您的环境存在异常` | 立即停止；同会话内不会自愈 |
| 业务层 | 打招呼额度、消息与标记频率 | 「今日沟通次数已达上限」 | 次日恢复；程序内对应暂停策略 |
| 账号层 | 异地登录、改密、滑块验证、403 | 登录失效、验证页 | 人工介入 |

## 2. 实测边界

本机实测（真实账号，签名正确的页面内请求）：

- 间隔 1.2 秒连续请求详情接口：第 6 条开始稳定返回 `code 37`。
- 命中后等待 90 秒，同会话仍为 `code 37`；换新浏览器会话立刻恢复。
- 触发后同一会话的搜索接口也一起失效，不只是详情接口。

公开项目 `boss-agent-cli` 的对照实验（2026-10-29）：间隔 15 秒时第 3 次搜索命中 37；30 秒两轮共 6 次通过；60/90 秒各 3 次通过。它现在的默认值是 30–60 秒。

两组独立观测指向同一结论：这是**短窗口速率**判定，不是总量配额。所以任何"提升吞吐"的批量化都会先撞墙。

## 3. 错误码处置

| 信号 | 含义 | 处置 |
|---|---|---|
| `code 37` + 环境存在异常 | 环境或频率 | 立即停止本轮，不重试、不刷新 token、不做登录；冷却后换新会话 |
| `code 36` | headless / 自动化特征 | 改用非 headless，并检查指纹 |
| `code 24` | 账号身份不匹配（非求职者端） | 换账号，不要重试 |
| `code 7` / 登录墙 / `/login` | 登录态失效 | 走登录助手 |
| `security.html?...code=37&seed=` | 页面级安检引导 | 等页面自动回到 `_security_check=1_...`，**不要**当成未登录 |
| 403 / `access-denied` | 账号或 IP 层拦截 | 停止，人工确认 |
| 「今日沟通次数已达上限」 | 业务额度 | 次日再跑，不要重试 |

## 4. 本项目已实现的保护

- `sageTime`：每 100 次操作暂停 15 分钟，随机化节奏。
- 打招呼额度用完：暂停 60 分钟再试，不连续冲击。
- 标记不合适：默认走本地记录，可配置为不写 BOSS。
- 采集模式（`jobCollectionOnly`）：只读遍历，不点沟通、不在 BOSS 上标记。
- 待聊清单：开聊由人确认后逐条执行，带「每次 N 个 + 每日上限」双约束。
- 登录态自愈：`__zp_stoken__` 失效时先保留身份 cookie、重开页面复检，避免不必要的重新登录。

## 5. 推荐设置

- 搜索/详情请求间隔不低于 30 秒；需要更快时，优先减少请求，而不是压缩间隔。
- 单日页面访问控制在 1000 次以内，详情页 900 次以内。
- 单日新增开聊 20–30 个，且一天内分布在不同时段，不要一次跑完。
- 固定使用同一个浏览器 profile，不要频繁换指纹或换 IP——环境漂移本身是风险信号。
- 出现 `code 37` 就停止当天剩余批量任务，第二天再用。

## 6. 不做的事

- 不绕过滑块、验证码、登录墙。
- 不伪造请求签名，不手工拼接口请求。
- 不多账号轮换来放大额度。
- 不把采集到的数据用于二次分发。

这些不是技术限制，是设计边界：绕过验证码等于把账号风险从"可能被限流"升级为"确定违规"。
